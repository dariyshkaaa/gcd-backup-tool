## 1. Паспортная часть и общие положения

### 1.1. Назначение документа

Настоящий регламент технического обслуживания определяет:

- **порядок** и **периодичность** работ по поддержанию работоспособности программного продукта **gcd-backup-tool**;
- **состав операций** планового (профилактического) и внепланового (инцидентного) технического обслуживания;
- **зону ответственности** специалистов, выполняющих работы;
- **инструменты** и **расходные материалы**, необходимые для выполнения операций;
- **критерии приёмки** выполненных работ.

**Цели внедрения регламента:**

| № | Цель | Как достигается |
|---|------|-----------------|
| 1 | Минимизация простоев | Регулярное резервное копирование и проверка целостности |
| 2 | Предотвращение потери данных | Плановое создание и ротация архивов конфигураций |
| 3 | Обеспечение безопасности | Контроль целостности через SHA-256 при каждом восстановлении |
| 4 | Быстрое восстановление после сбоев | Наличие актуальных резервных копий и пошаговых инструкций |
| 5 | Соблюдение требований сопровождаемости | Документирование всех операций в журнале |

### 1.4. Виды технического обслуживания

Все работы по ТО делятся на **два вида** по стратегии и частоте выполнения:

#### 1.4.1. Плановое (профилактическое) ТО — ППР

Выполняется **по календарю**, независимо от текущего состояния системы. Цель — предотвратить сбои до их возникновения.

| Пример операции | Периодичность |
|-----------------|---------------|
| Создание резервной копии конфигов | Ежедневно |
| Проверка целостности архива | Еженедельно |
| Ротация старых архивов | Ежемесячно |
| Обновление утилиты | По выходу новых версий |

#### 1.4.2. Внеплановое (инцидентное) ТО

Выполняется **по факту** возникновения ошибки, отказа или внештатной ситуации. Цель — восстановить работоспособность в кратчайшие сроки.

| Пример инцидента | Действие |
|-----------------|----------|
| Ошибка SHA-256 при восстановлении | Использовать более ранний архив |
| «Файл не найден» в задании cron | Проверить путь в настройках планировщика |
| Ошибка ввода в `gcd_tool` | Проверить формат входных данных |
| Откат после неудачного обновления | Восстановить конфиг из `*.bak` |

### 1.5. Порядок ведения журнала ТО

Все операции планового и внепланового ТО **обязательно фиксируются** в журнале. Формат записи:

```
[Дата и время] | [Операция] | [Исполнитель] | [Результат] | [Примечание]
```

**Пример:**

```
2026-10-21 02:00:15 | backup | Администратор | Успех | backups/config_backup_20261021_020000.tar.gz
2026-10-21 02:00:18 | verify | Администратор | OK | 3 файла проверены
2026-10-21 09:14:22 | restore | DevOps | Частично | 1 файл пропущен (ошибка SHA-256)
```

## 2. Технологические карты ТО

### 2.1. Плановое (профилактическое) ТО — ППР

#### Карта 1. Создание резервной копии конфигурационных файлов

| Параметр | Значение |
|----------|----------|
| **Наименование операции** | Создание резервной копии конфигурационных файлов |
| **Вид ТО** | Плановое (ППР) |
| **Периодичность** | Ежедневно, в 02:00 |
| **Исполнитель** | Администратор системы (автоматически через cron / Task Scheduler) |
| **Ожидаемая длительность** | 5–30 секунд (зависит от размера конфигов) |

**Пошаговый алгоритм:**

| Шаг | Действие | Команда / Инструмент |
|-----|----------|---------------------|
| 1 | Открыть терминал в папке проекта | `cd /opt/gcd-backup-tool` (Linux) или `cd C:\App\gcd-backup-tool` (Windows) |
| 2 | Запустить команду `backup` | `python src/backup_tool.py backup --source <путь> --dest <папка> --log <файл>` |
| 3 | Дождаться завершения | Программа выведет «Архив создан: …» |
| 4 | Проверить, что архив создан | `ls -lh /var/backups/myapp/` (Linux) или `dir C:\Backups\App` (Windows) |
| 5 | Проверить запись в журнале | `tail -5 /var/log/myapp_backup.log` |
| 6 | Зафиксировать операцию в журнале ТО | См. п. 1.5 |

**Используемые инструменты и расходные материалы:**

| Инструмент | Назначение |
|------------|-----------|
| `src/backup_tool.py` | Основной исполнитель операции |
| Модуль `tarfile` (Python) | Упаковка в `tar.gz` |
| Модуль `hashlib` (Python) | Вычисление SHA-256 |
| cron (Linux) / Task Scheduler (Windows) | Автоматический запуск |
| Дисковое пространство (≈ 50 МБ на архив) | Хранение архивов |

**Ожидаемый результат:**

- Создан файл `config_backup_YYYYMMDD_HHMMSS.tar.gz`.
- Внутри архива — `manifest.json` и подкаталог `files/` с копиями конфигов.
- В журнале (`--log`) — записи с указанием количества файлов и размеров.

**Критерий приёмки:** команда вернула код 0, архив существует, размер не нулевой.

#### Карта 7. Реакция на ошибку SHA-256

| Параметр | Значение |
|----------|----------|
| **Наименование операции** | Реакция на ошибку целостности архива |
| **Вид ТО** | Внеплановое (инцидентное) |
| **Периодичность** | При каждом инциденте |
| **Исполнитель** | Администратор системы |
| **Ожидаемая длительность** | 1–3 минуты |

**Диагностика:**

| Симптом | Возможная причина | Действие |
|---------|-------------------|----------|
| «✗ Хэш не совпадает: file.ini» | Диск повреждён; архив битый | Перейти к шагам ниже |
| «✗ Отсутствует: file.ini» | Файл не был включён в архив | Использовать другой архив |
| «В архиве нет manifest.json» | Архив повреждён | Использовать более ранний архив |

**Пошаговый алгоритм:**

| Шаг | Действие | Команда |
|-----|----------|---------|
| 1 | Проверить, что повреждён только один архив | `python src/backup_tool.py verify --archive <архив2>` |
| 2 | Если следующий архив тоже повреждён — проблема в диске | `fsck /dev/sdX` (Linux) или `chkdsk C:` (Windows) |
| 3 | Использовать более ранний целый архив для восстановления | карта 6 |
| 4 | Пересоздать свежую резервную копию | карта 1 |
| 5 | Зафиксировать инцидент в журнале | См. п. 1.5 |

**Критерий приёмки:** восстановлен рабочий конфиг из целого архива, новый архив создан, инцидент зафиксирован.

#### Карта 8. Реакция на ошибку «Файл не найден» в cron / Task Scheduler

| Параметр | Значение |
|----------|----------|
| **Наименование операции** | Диагностика сбоя автоматической резервной копии |
| **Вид ТО** | Внеплановое (инцидентное) |
| **Периодичность** | По факту инцидента |
| **Исполнитель** | DevOps-инженер |
| **Ожидаемая длительность** | 2–5 минут |

**Пошаговый алгоритм:**

| Шаг | Действие | Команда |
|-----|----------|---------|
| 1 | Проверить, что задание в cron / Task Scheduler существует | `crontab -l` (Linux) или открыть Task Scheduler (Windows) |
| 2 | Проверить логи cron | `grep CRON /var/log/syslog \| tail -20` |
